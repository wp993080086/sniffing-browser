# 计划：转换独立页面 + 任务持久化

- 日期：2026-11-12
- 触发：用户问「有单独的转换页面吗？在哪里看进度？在哪里看列表？」。
- 现状核对：没有独立页面。进度是下载项内 11px 小字，靠 `sourceTaskId` 关联下载记录；
  点完「转为 MP3」后菜单项消失（防重复入队）；下载页点「清空已完成 / 移除记录」后
  进度视图随之消失；`TranscodeQueue` 纯内存，重启即清空。
- 用户拍板两项：**加独立「转换」页** + **顺带做转换任务持久化**。

## 设计要点

| 决策 | 理由 |
| --- | --- |
| 入口放下载页 AppBar（`⇄` + 进行中角标） | 用户发起转换就在下载页，少一次跳转；主 AppBar 不再加第三个图标 |
| 入队后 SnackBar 带「查看进度」 | 菜单项会立刻消失，必须给一条直达路径，否则等于「点了没反应」 |
| 页面与下载记录解耦（只读 `TranscodeQueue`） | 移除/清空下载记录不该影响转换视图 |
| 持久化只存状态与结果，不存进度 | 进度每秒变几次，落盘无意义还磨损闪存 |
| `running` 重启后标「中断」 | ffmpeg 进程随应用死掉，假装在跑会让进度条永远停在某个百分比 |
| `pending` 重启后继续跑 | 它还没开始，源文件通常还在，续跑符合预期 |
| 写文件走临时文件 + rename | 写到一半被系统杀掉不会留下半个 JSON；坏文件读取失败按空处理 |
| 上限 100 条 | 转码低频，足够回溯，也防文件无限增长 |

## 落地顺序

1. `TranscodeStore`（JSON 读写 + 容错）
2. `TranscodeQueue`：`restore()` / `clearFinished()` / `activeCount` / 防抖落盘
3. `transcode_page.dart`
4. 入口：下载页 AppBar + SnackBar action；`app.dart` 启动时 `restore()`
5. 测试：store round-trip、坏数据、上限、重启恢复（running/pending）、移除与清空同步
6. 文档 / 规则 / 记忆
